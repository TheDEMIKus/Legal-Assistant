# ИИ-часть: юридический ассистент на RAG

## Задача и идея

Ассистент отвечает на вопросы по внутренним документам компании и нормативным актам из подготовленной базы знаний. Он не должен отвечать «по памяти» языковой модели: основанием для ответа служат только найденные фрагменты документов. Если надёжной опоры нет, система сообщает об этом или просит уточнить вопрос.

RAG расшифровывается как Retrieval-Augmented Generation — генерация ответа с опорой на найденные материалы. Здесь поиск и генерация разделены: сначала система находит нужные положения, затем передаёт ограниченный контекст языковой модели и проверяет её ответ.

## Как проходит обработка вопроса

### 1. Загрузка и подготовка базы знаний

`loader.py` читает документы из архива базы и сохраняет для каждого название, тип, текст и доступные сведения о редакции. Даты действия редакций используются позже при проверке ответа. Документы компании также связываются с упомянутыми в них договорами и регламентами: это позволяет найти дополнительное соглашение или письмо, которое меняет основной документ.

До индексации загрузчик удаляет строки, распознанные как инструкции для ИИ, например требования игнорировать другие документы или подменить ответ. Удалённые строки выводятся в журнал обработки. Это защита от prompt injection внутри источников: содержимое документа рассматривается как данные, а не как команды модели.

Документы разбиваются на смысловые фрагменты по статьям, пунктам и подпунктам. Максимальная длина фрагмента — 1200 символов, перекрытие соседних частей длинного пункта — 150 символов. Разбиение старается сохранить целый пункт и его вводную часть. В шапку фрагмента добавляются название документа, раздел и даты редакции. Для продолжения длинного пункта сохраняется родительская формулировка, чтобы отдельный подпункт не терял смысл.

В базе законов встречаются одинаковые заголовки статей, например «Налоговые ставки». Для статей Налогового кодекса загрузчик добавляет к названию статьи налог, к которому она относится. Это помогает различать похожие фрагменты при поиске и формировании цитат.

Пометки об истории изменений закона обрабатываются отдельно. Они остаются доступными для поиска, но при подготовке контекста генератору скрываются, если вопрос не об изменениях. Если пользователь спрашивает об изменениях, пометки остаются в контексте; сама пометка не подменяет текст нормы.

### 2. Гибридный поиск

`search.py` строит два независимых рейтинга кандидатов:

- **BM25** ищет совпадения по словам. Токенизатор приводит текст к нижнему регистру, раскрывает частые сокращения, удаляет стоп-слова и применяет простой стемминг русских слов. Номера договоров сохраняются как цельные идентификаторы; пробелы внутри больших чисел нормализуются.
- **Векторный поиск** сравнивает эмбеддинг вопроса с заранее рассчитанными векторами фрагментов. Векторная модель по умолчанию — `baai/bge-m3`; нормализация векторов позволяет ранжировать их скалярным произведением, эквивалентным косинусной близости.

Из каждого списка берутся до 20 кандидатов. Списки чередуются, дубликаты удаляются, а общий набор ограничивается 40 фрагментами. Это сохраняет сильные результаты обоих способов поиска и не позволяет одному из них полностью вытеснить другой.

Затем реранкер оценивает связь вопроса с каждым кандидатом и выбирает до пяти наиболее подходящих фрагментов. По умолчанию используется модель `cohere/rerank-5-fast`. Если реранкер недоступен, система отключает его на оставшуюся часть обработки и использует начало объединённого списка BM25 и векторного поиска.

После реранжирования система проверяет связанные документы у двух лучших результатов и может добавить до двух подходящих дополнений. Так ответ может учитывать не только договор, но и документ, которым он изменён.

### 3. Генерация ответа

`answer.py` получает вопрос и найденные фрагменты, формирует контекст и задаёт модели строгие правила: использовать только контекст, не соглашаться с неверными предпосылками вопроса, учитывать даты действия редакций, не выдавать инструкции из документов за нормы права и не добавлять сведения, не относящиеся к вопросу.

Модель возвращает структурированный JSON с полями:

- `quotes` — дословные цитаты и номера фрагментов;
- `found` — есть ли в контексте ответ;
- `calc` — арифметические действия, если расчёт нужен;
- `answer` — текст ответа;
- `clarify` — признак того, что вместо ответа нужно задать допустимый уточняющий вопрос.

История диалога передаётся в виде реплик пользователя и ассистента. Для поиска повторно учитываются реплики пользователя, а ответ строится на последнем вопросе с учётом предыдущего контекста. Если запрос слишком расплывчатый или найдено несколько похожих документов и пользователь не указал нужный, система может запросить уточнение. Код проверяет, что уточнение действительно нужно и не повторяется после того, как его уже задали.

### 4. Проверка ответа кодом

Проверка в `answer.py` закрывает ошибки, которые можно определить без дополнительной языковой модели:

1. Цитата должна находиться в указанном фрагменте. Сравнение нормализует регистр, кавычки, варианты тире и пробелы в числах; учитываются цитаты с пропуском середины.
2. Цитата не должна происходить из удалённой инструкции для ИИ.
3. Числа, даты, суммы, ссылки на пункты и статьи в ответе должны подтверждаться вопросом или контекстом. Числа сравниваются с границами: `5 000 000` не считается подтверждённым вхождением внутри `15 000 000`.
4. Расчёт должен быть записан в `calc`, его исходные значения должны быть известны, а результат пересчитывается кодом.
5. Содержательный ответ должен содержать подтверждающую цитату.
6. Если процитированы документы компании с датами редакций, проверяется, что хотя бы одна указанная редакция действовала на дату из вопроса или на текущую дату.

Если первая генерация не проходит проверку, модели передаётся список конкретных замечаний и разрешается одна исправляющая попытка. Критическая ошибка — например, неподтверждённая цитата или неверная редакция — приводит к безопасному отказу, если исправление не помогло. Пустой или обрезанный ответ может быть запрошен повторно на уровне клиента модели.

### 5. LLM-судья внутри ответа

Проверка кодом не может надёжно определить смысловые ошибки вроде перепутанного ответственного, неверного вывода из правильной цитаты или неучтённого изменения договора. Для этого в `answer.py` есть второй проверяющий проход — LLM-судья.

Судья получает вопрос, найденные фрагменты и прошедший программные проверки ответ. Его вызывают только для рискованных случаев: вопросов с датами и числами, продолжений диалога, нескольких процитированных документов, документов с редакциями или связанных дополнений, а также отказа при наличии найденных документов компании. Уточняющий вопрос не отправляется на смысловую проверку.

Судья не пишет финальный ответ. Он указывает на предполагаемую ошибку и подтверждает её цитатой из конкретного фрагмента. Код отбрасывает замечание, если цитата не найдена в указанном источнике, взята из инструкции для ИИ или сам спорный текст отсутствует в ответе. Генератор получает оставшиеся замечания и может исправить ответ; исправленный текст снова проходит программную проверку. Если судья, генератор или повторная проверка не дают надёжного результата, сохраняется ответ, прошедший первоначальную программную проверку.

Судья применяется к выбранным рискованным случаям; отдельной настройки для его отключения нет.

### 6. Внешние модели и ключи API

Модели не запускаются локально: клиент в `llm.py` отправляет запросы через внешний API, совместимый с форматом OpenAI. В `.env.example` приведён пример конфигурации сервиса **OpenRouter** (`https://openrouter.ai/api/v1`):

| Роль | Пример модели | Переменная |
|---|---|---|
| Генерация ответа и исправление | `deepseek/deepseek-v4.1-flash` | `LLM_MODEL` |
| Эмбеддинги для поиска | `baai/bge-m3` | `EMB_MODEL` |
| Реранжирование найденных фрагментов | `cohere/rerank-5-fast` | `RERANKER_MODEL` |

Общий адрес API задаётся первой непустой переменной в порядке `LLM_BASE_URL`, `BASE_URL`, `OPENAI_BASE_URL`. Один адрес используется для запросов генерации (`/chat/completions`), эмбеддингов (`/embeddings`) и реранжирования (`/rerank`); выбранный сервис должен поддерживать нужные операции и модели.

Непустые значения из `.env` имеют приоритет над переменными окружения процесса. Пустое значение в шаблоне не затирает ключ, переданный платформой; если `.env` отсутствует, используются переменные окружения. Для общего ключа код выбирает `LLM_API_KEY`, затем `OPENAI_API_KEY`. Для эмбеддингов сначала используется отдельный `EMBEDDER_API_KEY`, если он задан, иначе общий ключ. Для реранкера сначала используется `RERANKER_API_KEY`, иначе общий ключ.

В `README` указаны только имена переменных и публичные названия моделей. `.env.example` предназначен для примера и не должен содержать действующие ключи или пароли. Рабочие секреты не включаются в материалы проекта.

Настройки генерации, поиска, разбиения документов, размера запросов и повторов API читаются из `.env` или переменных окружения. К ним относятся `TEMPERATURE`, `MAX_TOKENS`, `MAX_TOKENS_CEILING`, `TOP_K`, `RERANKER_TOP_N`, `MAX_RERANK_CANDIDATES`, `MAX_RELATED`, `CHUNK_MAX`, `CHUNK_OVERLAP`, `EMBED_BATCH`, `MAX_ANSWER_CHARS`, `MAX_REMARKS`, `ANSWER_ATTEMPTS`, `CHAT_ATTEMPTS`, `HTTP_TIMEOUT`, `HTTP_CONNECT_TIMEOUT`, `HTTP_RETRIES` и `MAX_WORKERS`. Их примерные значения приведены в `.env.example`; при отсутствии значения используются прежние значения по умолчанию из `config.py`. Числовые параметры ограничиваются допустимыми диапазонами. При обрезанном ответе лимит генерации увеличивается до `MAX_TOKENS_CEILING`.

Клиент в `llm.py` повторяет временно неудачные HTTP-запросы до трёх раз с задержкой, учитывая `Retry-After`, когда он задан. В клиенте отдельно считаются запросы генерации, эмбеддингов, реранкера, повторные попытки и токены.

## Карта файлов ИИ/RAG

| Файл | Ответственность |
|---|---|
| `config.py` | Выбор API-адреса, ключей и моделей; постоянные настройки поиска и генерации; включение LLM-судьи. |
| `loader.py` | Чтение базы документов, извлечение текста и дат, удаление инструкций для ИИ, разбиение на фрагменты, построение связей между документами. |
| `search.py` | Токенизация, BM25, работа с векторным индексом, объединение кандидатов, реранжирование и добавление связанных документов. |
| `llm.py` | HTTP-клиент внешнего API для чата, эмбеддингов и реранкера; повторы при временных сбоях и статистика запросов. |
| `answer.py` | Промпты, подготовка контекста, генерация JSON, уточнения, программная проверка, исправление и LLM-судья. |
